📄 Slide 3 – Abstract

Executive Abstract

A concise 150–200 word summary covering problem, proposed solution, technology, implementation, and results.

Problem: Academic lecture notes, university exam question papers, and career roadmaps in engineering institutions remain severely fragmented across ad-hoc WhatsApp groups and unindexed Google drives, resulting in broken links, regulation confusion, and a wide industry skill gap.

Proposed Solution: The Department Resource Management System (DRMS) introduces a unified single-page platform integrating curriculum resources with an AI-powered Academic & Career Chatbot and visual career progression flowcharts.

Technology & Implementation: Built on HTML5, CSS3 Variables, Vanilla JavaScript, Node.js/Express REST APIs, and MongoDB Atlas. Incorporates Role-Based Access Control (RBAC), in-app PDF previewing, dynamic CRUD operations (Create, Read, Update, Delete) with live database sync, and a multilingual (English, Tamil, Tanglish) NLP chatbot.

Result: Eliminates study material retrieval latency by over 90%, equips students with clear industry benchmarks, and empowers faculty with real-time resource management and deletion safeguards.

🚨 Slide 4 – Problem Statement

Problem Statement & User Challenges

Clearly articulating the operational friction and technical limitations faced in existing college setups.

📂

1. Existing Problem

Lecture notes, syllabus copies, and past question papers are distributed across informal channels (WhatsApp groups, personal faculty Google Drives, and printouts).

✗ Files expire, access links break, and duplicates create version confusion.
👥

2. Difficulties Faced by Users

Students struggle to distinguish between academic regulations (R2021 vs R2025), often revising obsolete subjects.

✗ No transparent mapping between classroom syllabus and industry job roles.
✗ Physical queues at department offices for basic repetitive enquiries.
⚠️

3. Limitations of Existing Solutions

Conventional college websites function only as static notice boards without student interactivity.

✗ Lack of in-app document viewing (forces large file downloads).
✗ No real-time dynamic CRUD (updating or deleting outdated notes requires webmasters).

⚖️ Slide 6 – Comparative Analysis

Existing Systems and Limitations

Contrasting legacy academic communication methods with modern cloud-enabled requirements.

Existing Systems in Use

📱
WhatsApp Groups & Telegram Channels: Materials sent as loose attachments, quickly swallowed by casual messages and corrupted by cache cleaners.
🌐
Static Institutional Portals: Read-only, outdated web pages requiring vendor intervention for any content changes.
🏢
Manual Helpdesk Desks: Physical visits required to enquire about regulations, syllabus modifications, or elective choices.

Inherent System Limitations

⚠
No Real-time Content Updating or Deleting: When a professor modifies an answer key or removes obsolete notes, old copies continue circulating.
⚠
No Role-Based Access Control (RBAC): Anyone with a link can modify or delete cloud drives without accountability.
⚠
No Career Flowcharts: No contextual industry guidance, certifications catalog, or capstone project blueprint mapping.

📐 Slide 10 – System Design

System Design & Engineering Models

Architectural flowcharts: Use Case, Data Flow Diagram (DFD), ER Diagram, and Sequence Diagram.

1. Use Case Diagram

👤
Student: Search notes, view PYQs, bookmark materials, interact with AI Chatbot, explore career roadmaps.
👨‍🏫
Faculty: Upload unit lecture notes, provide syllabus links, review project proposals.
🔑
Admin: Manage user roles, perform dynamic CRUD (Add, Edit/Update, Delete), inspect inquiries.

2. Data Flow Diagram (DFD Level 0 & 1)

▸
Level 0 Context: User & Admin Entities ⇄ DRMS Boundary ⇄ MongoDB Atlas Cloud Store.
▸
Level 1 Sub-Processes: 1.0 Auth Verification ➔ 2.0 Academic Resource Cataloging ➔ 3.0 Chatbot NLP Intent Matching ➔ 4.0 Admin CRUD Handler.

3. Entity Relationship (ER) Model

🗄️
Entities: Department, Regulation, Subject, Resource (Notes/PYQs), User, JobRole, Roadmap, Certification.
🔗
Cardinality: 1-to-N (Department to Subjects), 1-to-N (Subject to Unit Notes), 1-to-N (Job Role to 4 Roadmap Stages).

4. Sequence Diagram (Data Flow)

⚡
Client Request: Browser sends GET /api/resources or Socket prompt to Express Server.
⚡
Validation & Fetch: JWT middleware authenticates ➔ Controller executes Mongoose query ➔ MongoDB Atlas returns document payload ➔ Client updates DOM in <15ms.
🧩 Slide 11 – Module Description

Module Description & Dynamic CRUD Operations

Modular breakdown of core components, including full Update and Delete capabilities recently enhanced.

🔐

1. User Auth & RBAC

Role-Based Access Control securing routes. Students get read-only browsing; Faculty can upload; Admins possess unrestricted CRUD rights.

🤖

2. AI Chatbot Assistant

Multi-lingual NLP engine (English, Tamil, Tanglish). Features quick suggestion chips, voice readout (TTS), instant subject suggestions, and deep navigation.

📚

3. Notes & PDF Viewer

Unit 1 to 5 drilldown with in-browser canvas PDF reader, zoom/print controls, university question paper archives, and personal bookmark pinboard.

🗺️

4. Career Flowcharts

68+ department-tailored career roadmaps with 4-phase progression, hands-on capstone project ideas, and interactive skill-gap analysis.

✏️ 🗑️

5. Admin Dynamic CRUD Engine (Update & Delete)

Recent Upgrades Fixed & Fully Operational:
• Create (Add): Faculty/Admins seamlessly add new lecture notes, model question papers, and roadmaps.
• Update (Edit): Instant edit modal allowing real-time modification of title, subject code, semester, unit, and PDF drive links.
• Delete (Remove): Safe deletion with modal confirmation preventing accidental data loss, accompanied by automated cache eviction.
